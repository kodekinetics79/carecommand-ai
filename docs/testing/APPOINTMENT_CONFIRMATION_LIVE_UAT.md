# CareCommand AI — Live Appointment-Confirmation Demo UAT

This is the commercial acceptance gate for one specific buyer-visible claim:

> CareCommand can call a patient about the patient's own upcoming appointment, verify the intended patient, record that the patient says they are coming, and show that confirmation back to clinic staff after reload.

It is **not** a load test, production campaign, HIPAA certification, permission to call arbitrary numbers, or permission to use real PHI. It uses one explicitly authorized destination and synthetic patient/appointment data only.

## What must be true before a call is allowed

The harness refuses to dial unless all of these are true:

1. `LIVE_TEST_CALLS_AUTHORIZED=true` and exactly one authorized E.164 destination is configured in the local process environment.
2. The live-test tenant and clinic IDs are explicit UUIDs.
3. The call cap is exactly one; per-call and aggregate duration are at most five minutes; provider-cost cap is at most USD 3.
4. Installed Google Chrome is used visibly (`E2E_USE_INSTALLED_CHROME=true`, not headless).
5. `PUBLIC_API_URL` is a public HTTPS endpoint that routes to the **same disposable UAT API/database** started by the harness.
6. The harness can authenticate its freshly seeded synthetic owner through `PUBLIC_API_URL`. This proves the public endpoint is not pointing at a different CareCommand deployment/database.
7. The exact pinned Retell agent/version is published and can be read back from Retell.
8. That provider version contains `record_recording_preference`, `verify_patient_identity`, and `confirm_appointment`.
9. Those tools point at the expected CareCommand function endpoint for the fixed synthetic clinic under `PUBLIC_API_URL`.

If any of these conditions fail, the test fails **before** a phone is dialed.

## Why a public callback is required

The generic live-voice smoke can prove that a phone rings while CareCommand polls Retell for lifecycle status. The appointment-confirmation demo is different: `confirm_appointment` is a Retell custom function invoked during the conversation, and it must call back into the exact CareCommand database that contains the synthetic patient and appointment.

Do not expose an unrestricted local development server directly to the internet. Use an approved, access-controlled HTTPS tunnel or a dedicated temporary UAT host that terminates TLS and forwards only to the intended UAT runtime. Retell signature verification remains mandatory at the CareCommand endpoint.

## Private environment values

Set private credentials only in the terminal session that starts the UAT. Do not paste them into chat, source files, screenshots, issues, test reports, or tracked `.env` files.

Required variables:

```bash
export DEPLOYMENT_PROFILE=demo
export RETELL_API_KEY='<restricted live UAT key>'
export RETELL_FROM_NUMBER='<Retell outbound number in E.164>'
export LIVE_TEST_RETELL_AGENT_ID='<published agent id>'
export LIVE_TEST_RETELL_AGENT_VERSION='<published integer version>'

export LIVE_TEST_CALLS_AUTHORIZED=true
export LIVE_TEST_EXECUTION_ID="appointment-confirm-$(date -u +%Y%m%dT%H%M%SZ)"
export LIVE_TEST_TENANT_ID='<fresh synthetic tenant UUID>'
export LIVE_TEST_CLINIC_ID='<fixed synthetic clinic UUID used by the published Retell tool URLs>'
export AUTHORIZED_TEST_PHONE_E164='<one explicitly authorized E.164 destination>'
export LIVE_TEST_RECIPIENT_ALLOWLIST="$AUTHORIZED_TEST_PHONE_E164"
export LIVE_TEST_EXPIRES_AT='<future ISO-8601 UTC timestamp, no more than 24h away>'
export LIVE_TEST_TIMEZONE='America/New_York'
export LIVE_TEST_WINDOW_START='09:00'
export LIVE_TEST_WINDOW_END='20:00'
export LIVE_TEST_MAX_CALLS=1
export LIVE_TEST_MAX_CALL_MINUTES=5
export LIVE_TEST_MAX_TOTAL_MINUTES=5
export LIVE_TEST_MAX_PROVIDER_COST_USD=3
```

The normal disposable database, Redis and JWT variables used by the repository test harness are still required. `PUBLIC_API_URL` must route back to that exact disposable API process.

## Run

```bash
npm run test:e2e:appointment-confirmation-live
```

The harness creates only synthetic records:

- patient: **Jordan Test**
- synthetic date of birth: **1990-01-15**
- phone: the one environment-authorized test destination
- future appointment: **Appointment confirmation demo**
- clinic/tenant: clearly named synthetic UAT records

The exact appointment time is generated by the harness and printed on the local test card.

## What the person answering the test phone does

When the phone rings:

1. Answer the AI recording-consent question **yes** for this attended synthetic test.
2. Confirm that you are **Jordan Test**.
3. When asked to verify identity, give the synthetic DOB **1990-01-15**.
4. After the receptionist states the appointment it is calling about, say clearly: **“Yes, I will attend that appointment.”**
5. End the call after the receptionist acknowledges the result and completes its required closing.

Do not give real medical, insurance, financial, or identifying information during this test.

## Pass criteria

The run is a **GO** only when all of the following are proven in one execution:

- exactly one provider call is created;
- the raw destination is not displayed in CareCommand browser/evidence surfaces;
- the target is a synthetic **patient**, not a generic lead;
- the target is visibly bound to the exact synthetic upcoming appointment;
- the provider receives the bound appointment context at dial time;
- identity verification succeeds through the signed live tool path;
- `confirm_appointment` writes a real confirmation to that same appointment;
- appointment scheduling status remains `CONFIRMED`/Booked — the patient confirmation is a separate fact;
- `patientConfirmationSource` is `receptionist_call`;
- `patientConfirmedCallLogId` links the confirmation to the exact call;
- audit contains `receptionist.identity.verified` and `receptionist.appointment.patientConfirmed`;
- provider intent and usage evidence exist;
- Scheduling visibly shows **Patient said they’re coming** and **Booked**;
- Scheduling still shows the confirmation after a browser reload;
- the appointment links back to **Open the call**;
- the outbound campaign's **Who has said they’re coming** card reports 1 of 1, attributed to this campaign call;
- desktop and Pixel 7 views remain usable;
- there are no browser console errors or unhandled 5xx API responses during the journey.

A phone that merely rings is **not** a pass.

## Customer demo sequence

Once the acceptance run is green, the buyer-facing demo should be kept short:

1. Open Scheduling and show Jordan Test's upcoming appointment as **Booked** with no patient confirmation yet.
2. Open AI Receptionist → Outbound and show the appointment-confirmation campaign.
3. Choose Jordan Test; show that CareCommand automatically selects or requires the exact upcoming appointment.
4. Click **Call** once.
5. Answer the authorized phone and complete the synthetic confirmation dialogue.
6. Return to Scheduling and refresh/reload.
7. Show **Patient said they’re coming** beside the still-Booked appointment and open the evidencing call.
8. Return to the campaign and show **1 of 1 patient has told us they’re coming** and that the confirmation came from this campaign.

Do not show provider IDs, hashes, raw database IDs, Retell internals, or raw phone numbers in the primary buyer journey.

## Fail / stop conditions

Stop and issue NO-GO for the demo if:

- the public callback does not reach the same synthetic UAT database;
- the pinned agent lacks the required tools or points at the wrong callback;
- a target can be created without the exact appointment binding;
- the AI reveals appointment details before the required consent/identity gates;
- identity verification cannot complete with the synthetic record;
- the patient says yes but no confirmation is durably written;
- a confirmation is inferred from `Appointment.status` instead of `patientConfirmedAt`;
- the raw destination leaks to the browser/evidence;
- the journey requires SQL, a raw API request, or developer database repair;
- more than one live call is attempted;
- any safety, DNC, suppression, quiet-hours, tenant, identity, or provider-signature guard is bypassed.

## Cleanup

The disposable test database is torn down by the repository wrapper. After the run, clear the process-scoped authorization, public UAT route, and secrets, and confirm no call remains active in Retell. Do not reuse the live authorization for another recipient or another day.
